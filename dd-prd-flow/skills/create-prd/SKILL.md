# Create Product Requirements Document

根据当前讨论、用户提供的初版 PRD 和已有资料，创建精简但可拆解的中文 PRD，默认保存到 `docs/PRD.md`。PRD 的主要读者是独立开发者，次要读者是后续继续生成 Feature Specification、任务拆解和实现计划的 AI。

## 适用场景

- 用户描述了一个产品想法，需要整理成 PRD。
- 用户提供了初版 PRD、历史需求讨论或零散资料，需要融合重写为新的权威版本。
- 用户需要明确 MVP、后续范围、不做什么，以及独立开发者实现时的取舍。
- 后续会基于 PRD 继续生成多个 feature spec、任务拆解或实施计划。

## 工作流

1. 收集输入：读取当前对话、用户提供的初版 PRD 或需求材料；如果用户要求更新已有项目 PRD，再读取 `docs/PRD.md`。
2. 融合重写：把讨论、旧 PRD 和可推断上下文合并为新的权威 PRD，而不是保留旧结构做小修补。
3. 判断歧义：只有当产品方向、目标用户、核心价值或 MVP 边界不清楚时，才提出少量高价值澄清问题。
4. 记录假设：信息不足但可合理推进时，直接生成 PRD，并在“假设、待确认问题、风险”中明确标注。
5. 拆分 feature：为核心能力分配稳定的 feature id，并说明优先级、依赖和后续 spec 拆分建议。
6. 保存输出：默认创建或更新 `docs/PRD.md`，除非用户指定其他路径。

## PRD 结构

1. 产品概述
2. 问题背景与目标用户
3. 产品目标与非目标
4. MVP 范围、后续范围、不在范围
5. 核心用户流程
6. 功能地图
7. 用户故事与验收标准
8. 关键概念、数据对象或内容模型
9. 成功指标
10. 非功能需求
11. 技术、资源与独立开发者约束
12. 假设、待确认问题、风险

## 功能地图要求

功能地图要让后续 `generate-spec` 能直接选择单个 feature 继续展开。每个核心功能至少包含：

- `feature id`：使用稳定、简短、可作为文件名来源的英文 kebab-case，例如 `auth-login`。
- 优先级：`P0`、`P1` 或 `P2`。
- 功能说明：说明用户要完成什么，以及为什么需要它。
- 依赖关系：列出依赖的前置功能、数据对象或外部服务；没有则写“无”。
- Spec 拆分建议：说明后续应生成哪个 `docs/specs/<feature-name>.md`。

## 质量标准

- 面向独立开发者，语言务实，避免企业化空话和过度流程化表达。
- PRD 主要写“做什么、为什么、边界是什么”，不要提前写过细实现方案。
- 明确区分 MVP、后续增强和不在范围内的内容。
- 每个核心 feature 都要足够独立，能继续生成 Feature Specification。
- 用户故事必须绑定可判断的验收标准。
- 约束要贴近个人开发现实，包括时间、维护成本、第三方依赖、数据复杂度和验证成本。
- 输出前检查 PRD 是否具体、可执行、可追溯，并能支撑 `generate-spec` 继续工作。
